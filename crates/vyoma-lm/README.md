# vyoma-lm — the first integrated model (stored SSM + generated FFN)

> Phase-1. Combines the Phase-0 findings into an Vyomarudra-shaped model and asks the
> real question: on a task where a **big FFN genuinely helps**, can the fractal
> Eternal Seed *generate* that FFN cheaply — matching a dense model and beating a
> same-footprint plain one?

## Architecture

```
token embed (stored)
  → diagonal SSM mixer over the sequence (stored, lean — Pillar 2)
  → FFN  d_model → d_ff → d_model, residual   (GENERATED by the fractal seed — Pillar 1)
  → output head (stored)
```

Only the FFN — the large, redundant mass — is generated. The lean SSM core is
stored (Phase-0 showed generating it loses). This is the division of labor from
`docs/english/06-refined-architecture.md`.

## Run it

```bash
cargo build --release -p vyoma-lm
# precondition check: does FFN width drive quality?  (dense-only sweep)
STEPS=600  DM=64  SEQ=48 DATASET=text  MODE=diag  ./target/release/vyoma-lm
# the real test: generated FFN vs same-footprint plain vs dense
STEPS=3000 DM=128 DFF=512 SEQ=48 DATASET=text MODE=sweep ./target/release/vyoma-lm
```
Env: `STEPS DM DFF SEQ DATASET(text|arith) MODE LAYERS TOKENIZER(char|bpe)`. Text
corpus = `data_cache/tinyshakespeare.txt` (fetched via `curl -skL`).

| `bpb` | bits-per-byte (tokenizer-independent eval) | BPE 2.14 vs char 2.85 |

| **`retro`** | **E2 closed with OUR retriever** (`vyoma-embed`), not the oracle: our encoder fetches the fact, our LM reads & answers | memorize collapses, retro(ours) beats it ✅ |
| **`retrolm`** | the retro loop on **REAL language**: `[neighbor][SEP][passage]` blocks; ablation of retrieved-neighbor vs random-neighbor; scored by masked next-char acc + bits/char (env `RSEEDS`/`RP`/`RSEQ`) | retro < random by −0.040 bits/char over 2 seeds (small, consistent, noisy) |

## Findings

### Arithmetic was a dead end — by construction

The first task (char-level `a+b=c`) turned out **not FFN-capacity-bound**: a
`dff=6` FFN scored ~as well as `dff=512` (0.307 vs 0.324 answer-digit acc). With
no big *needed* FFN mass, generation had nothing to win on and only added
optimization overhead → it trailed a same-size plain model. Lesson: **small toys
rarely need a big FFN, so they can't stage the generate-the-FFN win.**

### Real text IS FFN-capacity-bound (precondition met)

On tiny-shakespeare (vocab 65), a wider FFN monotonically improves quality —
so generating it is a meaningful test:

| FFN width | total params | loss | next-char acc |
|---|---|---|---|
| 8 | 9,737 | 2.247 | 34.0% |
| 32 | 12,833 | 2.178 | 36.6% |
| 128 | 25,217 | 2.143 | 37.5% |
| 512 | 74,753 | 2.098 | 38.0% |

*(dm=64, 600 steps — modest but monotonic; the effect grows with dm and training.)*

### The generation test on text — honest negative

dm=128, dff=512 (FFN mass 131,712), 3000 steps. Dense = **49.3%**.

| FFN compression | seed | gen-FFN | plain (same footprint) | edge |
|---|---|---|---|---|
| 26.9× | 4,905 | 39.81% | 39.69% (dff=18) | +0.001 |
| 49.1× | 2,685 | 39.16% | 39.79% (dff=9) | −0.006 |
| 137.3× | 959 | 37.72% | 38.05% (dff=3) | −0.003 |

**gen-FFN ties a same-size plain FFN at every compression, and both sit ~10 pts
below dense.** The dramatic MNIST edge (gen ≫ plain) did **not** transfer to
language FFNs — these weights are far less fractally-compressible. Fractal
generation gives no advantage over just using a small FFN here.

Scope: 1-layer, char-level, diagonal SSM, 3000 steps — suggestive, not final. But
it's the first direct language test, and it's negative. This pushes the design
toward the doc's **hybrid fallback** (moderate generation × quantization ×
retrieval), unless scale/multi-layer restores the edge.
