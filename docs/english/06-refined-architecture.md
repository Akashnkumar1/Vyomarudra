# 06 — Refined Architecture (Evidence-Updated)

The original five pillars (doc 02) were the *hypothesis*. This doc updates them
with what Phase-0 experiments actually showed, and turns the results into a
concrete Phase-1 build. It supersedes doc 02 wherever they disagree; doc 02 stays
as the original vision of record.

> **The design law Phase-0 established:** *generative weights pay off in exact
> proportion to the target's parameter redundancy.* Compress the redundant mass;
> store the efficient, sensitive parts directly.

---

## What Phase-0 proved, pillar by pillar

| Pillar | Original claim | Phase-0 evidence | Status |
|---|---|---|---|
| **1. Eternal Seed** (generative weights) | store rules, not weights; 100–1000× | Fractal seed: **212× on MNIST, 423× improving-with-scale** for feedforward mass; edge over a same-size model grows with compression | ✅ **validated for feedforward mass** |
| — same, on lean cores | generate everything | **SSM weights resist generation** — a small stored SSM beats a generated one (pure & hybrid) | ❌ **falsified for recurrent cores** |
| **2. SSM backbone** | constant-memory sequence model | diagonal SSM trains fine and is **parameter-efficient** — which is exactly why you should *store* it, not generate it | ✅ keep, and keep it stored |
| **3. Trinity** (sparse + symbolic) | MoE + symbolic lattice | not yet tested | ⬜ open |
| **4. Ontological Store** (RETRO) | knowledge on disk | not yet tested | ⬜ open (E2) |
| **5. Self-evolution** | bounded deltas | not yet tested; the SSM's `A=σ(·)∈(0,1)` already demonstrates build-in stability | ⬜ open |

Two data-dependent facts also emerged:
- **Achievable compression tracks data redundancy** (MNIST ~200× vs Fashion ~76× at ≤10% loss). The frontier ceiling will depend on how redundant language/reasoning weights are.
- Generated networks need an **architecture-derived per-group init prior** (O(1) storage) or they start dead.

## The refined architecture (Vyomarudra v2)

The evidence forces a clean **division of labor by parameter-redundancy**:

```
            ┌───────────────────────────────────────────────┐
  STORED    │  Lean SSM backbone   (Pillar 2, parameter-      │
  (small,   │  efficient, dynamical, sensitive → store it)    │
  direct)   │  + embeddings + output head + recurrence params │
            └───────────────┬───────────────────────────────┘
                            │ per-position hidden states
            ┌───────────────▼───────────────────────────────┐
  GENERATED │  Large FFN / MoE-expert mass   (Pillar 1)        │
  (fractal  │  This is where a frontier model keeps most of    │
  seed)     │  its parameters, and it is provably redundant →  │
            │  generate it from the Eternal Seed on demand.    │
            └───────────────┬───────────────────────────────┘
                            │
            ┌───────────────▼───────────────────────────────┐
  EXTERNAL  │  Ontological Store (Pillar 4, disk, RETRO) —    │
  (disk)    │  untested; the knowledge, not the skill.         │
            └───────────────────────────────────────────────┘
```

Why this is the right shape given the data: in a real transformer/MoE, the FFN
and expert layers are the **majority of parameters** and are the most redundant —
so generating them is where the 8 GB win actually comes from. The SSM backbone is
already tiny; generating it loses. This isn't a compromise — it's the architecture
the experiments *designed for us*.

## Phase-1 experiment: `vyoma-lm` (the first integrated model)

**Goal:** show the division of labor works on a *capacity-hungry* task — one where
a bigger FFN measurably helps, so generating it is meaningful (row-MNIST didn't
need a big FFN, which is why the toy couldn't show the hybrid win).

**Task.** Char-level next-token prediction on a procedurally-generated, fully
offline, capacity-demanding corpus (candidate: arithmetic `a+b=c\n`, ~13-char
vocab — genuinely requires computation, crisp answer-digit accuracy metric).

**Model (1 block to start).**
```
token embed (stored)
  → diagonal SSM mixer over the sequence (stored, all positions)
  → FFN  d_model → d_ff → d_model, residual  (GENERATED by fractal seed; d_ff large = the mass)
  → output head (stored / tied)
```

**Comparisons (the honest test, unchanged).** At matched total footprint
(stored + seed): generated-FFN model vs. a plain model of the same footprint vs.
the dense upper bound. Sweep d_ff and seed size.

**Success / kill signal.**
- ✅ the generated-FFN model matches the dense model's answer accuracy while its
  FFN mass is compressed ≥10× and total footprint < the plain baseline's.
- ❌ if a same-footprint plain model wins here too, then the redundancy principle
  does not extend to language-relevant FFNs at this scale — a real result that
  would send us back to the compression-vs-redundancy question with harder data.

**Then:** scale d_ff (test the improves-with-scale law on a capability-meaningful
task), add MoE routing (Pillar 3), and only later wire the Ontological Store (E2).
